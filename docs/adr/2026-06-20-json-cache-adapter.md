# JSON Cache adapter lifecycle and persistence

The Cache context adds a `JsonCache` adapter for local file-backed cache persistence while keeping Redis as the shared production cache backend. `JsonCache` reuses the in-memory cache store, loads strictly during the Instance start hook using a compiled Valleyed JSON pipe, rejects `get`/`set`/`delete` before startup, persists absolute expiry timestamps, and writes eagerly with atomic renames after mutations and expiry cleanup, including expired entries discovered by `get`. Each foreground operation and background expiry sweep acquires the adapter lock file, reloads the latest JSON snapshot, applies its read or write, and persists only when the operation changes the cache. Load validation rejects malformed JSON and wrong known-field types while stripping unknown extras for forward compatibility. Any failed foreground cleanup or mutation write rejects the cache operation; a failed background expiry-sweep write crashes the Instance because there is no caller promise to reject. The adapter remains a local persistence option rather than a distributed cache, but lock/reload/write semantics prevent stale same-file adapter instances from losing each other's keys.
